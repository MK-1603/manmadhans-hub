## 5. Founder Admin Seed System

The Founder Admin account is created once via a seed script. This account is permanently reserved and cannot be deleted or demoted. All other Admin accounts created afterward have the exact same privileges.

```typescript
// seed/founderadmin.ts
const founderAdmin = {
  username:       'saikrishnanmk1603',
  hub_id:         'MK1603',
  email:          'admin@manmadhanshub.com',
  password:       bcrypt.hash('welcome@123', 12),
  role:           'admin',               // Same role as all other admins
  is_founder:     true,                  // Cannot be deleted or demoted
  identity_code:  'MK1603',
  first_login:    true,
}
// Hub Key is generated and stored in hub_keys table during seed
// Hub Key is printed to console ONCE — Founder Admin must record it securely
```

**Seed command:** `npm run seed:founderadmin`

> The seed script is idempotent. Running it twice does not create a duplicate. MK1603 is permanently reserved. The `is_founder` flag prevents deletion from any UI or API call. Hub Key is printed once at seed time.

## 6. Authentication System — 3-Step Login

### Full Login Flow

```
User visits / (Landing Page)
      ↓
Clicks "Enter Hub →" → /login
      ↓
STEP 1: Enter email + password (welcome@123 for new users)
      ↓
POST /auth/login → validate credentials
      ↓
Account suspended? → redirect to /suspended
      ↓
Credentials valid → STEP 2: Hub Key prompt appears at /hub-key
      ↓
POST /auth/verify-hub-key → validate Hub Key against stored hash
      ↓
3 wrong Hub Key attempts → 15-min lock + Admin notified
      ↓
Hub Key valid → First login? → Begin 6-step onboarding (/welcome)
      ↓
Onboarding complete → Issue JWT access token (15 min) + refresh token (7 days)
      ↓
Store refresh token in Redis + HttpOnly cookie
      ↓
Redirect to /dashboard
```

### Token Strategy

| Token | Lifetime | Storage |
|-------|----------|---------|
| Access token | 15 minutes | Memory (Zustand) |
| Refresh token | 7 days | HttpOnly cookie + Redis |
| Session record | Per device | PostgreSQL sessions table |
| Hub Key half-session | 5 minutes | Server-side only |

### Session Expiry Behaviour

| Event | Behaviour |
|-------|-----------|
| Token refresh succeeds | Seamless background refresh — user notices nothing |
| Token refresh fails | Silent redirect to /login with toast: "Session expired. Please sign in again." |
| Return URL | After re-login, user is returned to the page they were on |

### Password Rules

| Rule | Detail |
|------|--------|
| Default password | `welcome@123` — same for every new invited user |
| First login | Forced password change at step 3 of onboarding |
| After change | `welcome@123` is permanently invalidated for that account |
| New password | Min 8 chars · 1 uppercase · 1 number · 1 special character |

## 7. Hub Key 2FA System

The Hub Key is a **permanent, system-generated unique second authentication factor** assigned to every user at account creation. It is not time-based — it is a fixed personal key included in the invitation message.

### Hub Key Format

```
HK-[4 chars]-[4 chars]-[4 chars]

Examples:
  HK-M4K7-B9RX-2QP3
  HK-T8NV-5WJK-6RD1

Character set: ABCDEFGHJKMNPQRSTUVWXYZ23456789
(Excludes: 0, O, I, 1, L — to prevent transcription errors)
```

### Hub Key Generation

```typescript
function generateHubKey(): string {
  const chars = 'ABCDEFGHJKMNPQRSTUVWXYZ23456789';
  const seg = (n: number) =>
    Array.from({ length: n }, () =>
      chars[Math.floor(Math.random() * chars.length)]
    ).join('');
  return `HK-${seg(4)}-${seg(4)}-${seg(4)}`;
}
```

### Hub Key Storage

| Property | Detail |
|----------|--------|
| Storage | `hub_keys` table — stored as bcrypt hash (cost 12) |
| Plain key | Never stored — shown once in the invitation message |
| Comparison | bcrypt.compare(inputKey, storedHash) at step 2 of login |
| Last used | `last_used_at` updated on every successful verification |

### Hub Key Failure Handling

| Event | Behaviour |
|-------|-----------|
| 1st wrong key | Toast: "Incorrect Hub Key. 2 attempts remaining." |
| 2nd wrong key | Toast: "Incorrect Hub Key. 1 attempt remaining." |
| 3rd wrong key | 15-min account lock · Toast: "Hub Key locked. Contact your Hub administrator." |
| Lock expiry | Auto-unlocks after 15 minutes |
| Override | Any Admin can manually unlock from /admin/users/[id] |
| Audit | All failures and locks recorded with IP address |

### Hub Key Reset (Lost Key)

Any **Admin** can reset a Hub Key.

```
User contacts admin → reports lost Hub Key
      ↓
Admin opens /admin/users/[id] → clicks "Regenerate Hub Key"
      ↓
Confirms in slide-to-confirm dialog
      ↓
System generates new Hub Key → immediately invalidates old key
      ↓
New Hub Key displayed once on screen → Admin copies it
      ↓
Pre-filled invitation message prepared with new Hub Key
      ↓
Admin sends via WhatsApp/Telegram
      ↓
User must use new Hub Key within 72 hours
      ↓
Reset logged in audit log
```

### DB Table — hub_keys

```sql
CREATE TABLE hub_keys (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       UUID REFERENCES users(id) ON DELETE CASCADE UNIQUE,
  key_hash      VARCHAR(255) NOT NULL,
  created_at    TIMESTAMP DEFAULT now(),
  last_used_at  TIMESTAMP,
  reset_count   INTEGER DEFAULT 0,
  reset_by      UUID REFERENCES users(id),
  reset_expires TIMESTAMP
);
```


| Property | Detail |
|----------|--------|

## 28. Similar Tools System

Tag-based, pure SQL — no AI or vector search.

**Location:** Inline section at bottom of `/tools/[slug]`

```sql
-- Find up to 4 tools sharing tags or same sector
SELECT t.*, COUNT(shared_tag) AS match_score
FROM tools t
WHERE t.id != :current_tool_id
  AND t.tool_status = 'active'
  AND (
    t.sector_id = :current_sector_id
    OR EXISTS (
      SELECT 1 FROM unnest(t.tags) AS tag
      WHERE tag = ANY(:current_tags) LIMIT 2
    )
  )
GROUP BY t.id
ORDER BY match_score DESC, t.rating_avg DESC
LIMIT 4;
```

| Rule | Detail |
|------|--------|
| Cache | Redis — 1 hour TTL per tool slug |
| Section title | "You might also explore" |
| Fallback | Section hidden if fewer than 2 matches found |

## 74. Database Migration Strategy

All schema changes managed via **Drizzle Kit** migrations, tracked in git.

```
packages/db/schema/    ← Drizzle TypeScript schema definitions
packages/db/migrations/
  0001_initial_schema.sql
  0002_add_hub_keys.sql
  0003_add_tool_screenshots.sql
  0004_add_tool_flags.sql
  0005_add_pricing_history.sql
  0006_add_platform_announcements.sql
  0007_add_hub_movie.sql
  meta/
```

| Rule | Detail |
|------|--------|
| Never delete migration files | Create a reversing migration instead |
| Additive first | Add nullable columns before making required |
| Test before production | Always apply to staging + run full tests first |
| Rollback SQL | Every migration PR must include reverting SQL |
